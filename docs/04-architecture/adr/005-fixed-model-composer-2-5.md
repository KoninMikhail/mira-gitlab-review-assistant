## Контекст

Качество ревью, стоимость, бюджет контекста при декомпозиции MR и **воспроизводимость
метрик** зависят от модели. Cursor поддерживает `model: "auto"` и несколько моделей
через `--list-models` / `Cursor.models.list()`. Нужно зафиксировать базовую модель
(вопрос **Q-7**) и правила её переопределения.

## Решение

**Базовая модель проекта — Cursor Composer 2.5 (`composer-2.5`).** Явно задаётся во
всех движках:

- CLI: `--model "composer-2.5"`;
- SDK: `model: { id: "composer-2.5" }`.

**Не использовать `model: "auto"` по умолчанию.** Фиксированная модель вместе с
`prompt_version` и `partition_version` входит в ключ идемпотентности state store и
делает метрики сопоставимыми во времени.

Переопределение модели — только **осознанно** через политику проекта (например,
более сильная модель для крупных MR); дефолт системы остаётся `composer-2.5`.

При настройке окружения проверять доступность модели для `CURSOR_API_KEY`.

## Последствия

**Плюсы:**

- Предсказуемое качество и стоимость;
- идемпотентность: смена модели = новый прогон, не «тихое» изменение результата;
- декомпозиция и `max_chunk_tokens` калибруются под контекст Composer 2.5.

**Минусы:**

- Нет автоматического выбора «лучшей» модели под задачу;
- при устаревании `composer-2.5` потребуется осознанная миграция и перекалибровка
  промптов/бюджетов.

**Включает:** поле `model` в `ReviewResult`; запись `prompt_version` +
`partition_version` в `MR_REVIEW` (см. [007-sqlite-state-store.md](./007-sqlite-state-store.md)).

## Альтернативы

| Вариант | Почему отклонён |
| --- | --- |
| `model: "auto"` | Невоспроизводимые метрики и идемпотентность; непредсказуемая стоимость |
| Разные модели по умолчанию в CLI vs SDK | Расхождение качества между фазами без явной политики |
| Self-hosted LLM без Cursor | Отдельная большая развилка; только запасной план при запрете egress |
