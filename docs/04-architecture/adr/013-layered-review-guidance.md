# 013. Трёхслойная модель правил ревью (baseline + стек-профиль + repo-local)

- Статус: Принято (Accepted)
- Дата: 2026-06
- Контекст-ссылки: [004-review-engine-port-cli-then-sdk.md](./004-review-engine-port-cli-then-sdk.md), [005-fixed-model-composer-2-5.md](./005-fixed-model-composer-2-5.md), [007-sqlite-state-store.md](./007-sqlite-state-store.md), [../../03-reference/review-profiles.md](../../03-reference/review-profiles.md)

## Контекст

В организации десятки/сотни репозиториев на разных стеках (Python, Java, Node,
frontend, Go, …). Их нужно ревьюить **по-разному**, но единый промпт
(`prompts/review.v1.md`) не учитывает специфику стека, а policy YAML задаёт только
**механику** (триггеры, строгость, globs, бюджет, модель), а не «что искать».

Нужно простое и понятное место и **формат** для правил ревью, который:

- даёт org-wide baseline и стек-специфику централизованно;
- позволяет командам владеть спецификой своего репозитория;
- не требует «километровых JSON с кодом» — авторам нужен человекочитаемый формат;
- не ломает гексагон и идемпотентность.

Рассматривались два предложения: (1) отдельный центральный репозиторий правил;
(2) папка `.mira/` в каждом репозитории.

## Решение

**Трёхслойная резолюция guidance**, где слои имеют разную природу хранения:

| Слой | Что | Где | Формат |
| --- | --- | --- | --- |
| A — базовый промпт | роль + универсальные принципы | `prompts/review.v1.md` (с ботом) | Markdown + `{{плейсхолдеры}}` |
| B — стек-профиль | «на что смотреть в стеке» | `profiles/<name>.md` (централизованно) | Markdown-чеклист |
| C — repo-local | специфика репозитория | `.cursor/rules/*.mdc`, `AGENTS.md` (в репо) | нативный формат Cursor |

- A + B склеивает бот и инжектит в промпт (`{{profile_guidance}}`).
- **C движок читает сам**: `cursor-agent` запускается в чекауте ветки MR (`cwd =
  workspaceDir`) и нативно подхватывает `.cursor/rules`/`AGENTS.md` — **новый формат
  изобретать не нужно**. При конфликте repo-local (C) приоритетнее профиля (B).
- Выбор профиля — поле `profile` в **существующей** policy (`defaults` /
  `projects.<path>`); одна строка вместо нового конфига.
- **Механика остаётся в YAML**, «что искать» — в **Markdown** (не JSON). JSON — только
  контракт вывода (`schema/findings.schema.json`).

**Идемпотентность:** отпечаток профиля (`<name>@<sha8>` от тела файла) подмешивается
в `promptVersion` ключа (`review.v1+python@a1b2c3d4`). Правка профиля → новый ключ →
переревью затронутых MR. Слой C в ключ не входит (версионируется вместе с кодом,
меняет SHA сам).

## Последствия

**Плюсы:**

- Org-governance (A+B централизованы) и владение командами (C в репо) одновременно.
- Один профиль на стек — без дублирования по сотням репозиториев.
- Формат человекочитаемый; переиспользуем нативные `.cursor/rules` вместо своего `.mira/`.
- Fail-fast: ссылка на несуществующий профиль падает на старте.
- Минимальные изменения кода, гексагон не нарушен (загрузка профилей — слой config/adapter, `core` чист).

**Минусы:**

- Слой C зависит от того, что headless `cursor-agent` действительно загружает project
  rules в данном режиме — **проверить на пилоте** (см. ниже).
- Авто-детект стека по файлам (`package.json`, `pom.xml`, …) пока **не** реализован —
  на старте профиль задаётся явно (`profile:`), согласуется с `discovery: explicit`.
- Профиль — на весь проект; разный профиль на под-дерево монорепо решается glob-скоупом
  слоя C (`.cursor/rules` с `globs`), не полем `profile`.

**Включает:** `ProjectPolicy.profile`; `src/config/profiles.ts`; директория `profiles/`;
`{{profile_guidance}}` в промпте; `resolveGuidanceVersion` в пайплайне; env
`MIRA_PROFILES_DIR`.

## Альтернативы

| Вариант | Почему отклонён (как единственный) |
| --- | --- |
| Только центральный репозиторий правил | Дрейф от кода, команды не владеют спецификой, не branch-aware, нужна инфра синка |
| Только `.mira/` в каждом репо | Надо трогать все репо, дублирование по стекам, нет baseline, изобретение формата поверх существующих `.cursor/rules` |
| Правила в JSON/большом конфиге | Нечитаемо для авторов; движок — LLM, ему естественнее проза; JSON оставлен только для вывода находок |
| Авто-детект стека сразу | Лишняя сложность на старте; explicit `profile:` проще и согласован с explicit discovery |

## Открытые вопросы (для пилота)

- Подтвердить, что `cursor-agent -p` в чекауте загружает `.cursor/rules` (always /
  glob-scoped) и `AGENTS.md`. Если нет — слой C дочитывать явно в промпте.
- Авто-детект профиля по маркер-файлам (`match_globs` во frontmatter уже зарезервирован).
