# Глоссарий домена

Термины предметной области Mira Review Bot — **концептуально**, без сигнатур TypeScript.
Точные типы, поля и схемы — в [../03-reference/domain-types.md](../03-reference/domain-types.md)
и [../03-reference/finding-fingerprint.md](../03-reference/finding-fingerprint.md).

## Внешние сущности

### MR (Merge Request)

Запрос на слияние в GitLab. Единица, вокруг которой строится ревью: diff, метаданные,
комментарии. Идентифируется парой `(project_id, mr_iid)`.

### Задача / карточка (TaskCard)

Единица работы в Kaiten, которую реализует MR. Mira читает заголовок, описание и
**критерии приёмки** — чтобы проверять не только «качество кода», но и соответствие
требованиям. Если карточка не найдена, ревью **деградирует** к анализу только diff.

### Движок ревью (Review Engine)

Cursor как «мозг» анализа: CLI headless (MVP) или SDK (прод). Получает
`ReviewContext`, возвращает `ReviewResult`. За портом — можно менять реализацию без
правок ядра.

### Адаптер

Реализация порта для конкретной внешней системы (`GitLabReader`, `KaitenTracker`,
`CliHeadlessEngine`, …). Ядро знает только интерфейс, не детали API.

### Publisher

Компонент, который **публикует** результат ревью наружу (комментарии MR, сводка,
inline-дискуссии). Сейчас — **dry-run** через лог; в фазе 2 — GitLab REST под
bot-аккаунтом.

### Воркспейс (workspace)

Изолированный checkout репозитория на head-коммите MR. Создаётся на время одной
задачи ревью и удаляется после. Даёт агенту воспроизводимый контекст файлов.

## Задача ревью и контекст

### JobKey

Якорь идемпотентности: конкретный MR, **закреплённый за конкретным head SHA**.
Один и тот же `(project, mr, sha)` не ревьюится повторно без явного force (например,
`@mira review --force`).

### ReviewJob

Единица работы в очереди: `JobKey` плюс метаданные происхождения — **какой триггер**
(`open`, `ready`, `push`, `chatops`, `poll`, `manual`) и когда задача поставлена в
очередь.

### TriggerKind

Причина постановки задачи в очередь. По умолчанию автоматически — только первичное
состояние MR (`open`, `ready`); пуши и ручной `@mira review` настраиваются отдельно.

### ReviewContext

Всё, что нужно движку для анализа **одного MR или его части**: метаданные MR, diff,
список изменённых файлов, опционально связанная `TaskCard`. Материализуется во
воркспейсе (промпт, `context.json`, файлы репозитория).

### ReviewUnit

Срез работы после **декомпозиции** (partition). Большой MR режется на несколько
юнитов по бюджету контекста; движок вызывается **на каждый юнит**, результаты
сводятся агрегатором. В MVP — упрощённый режим «один юнит на MR» с чанкингом по
размеру.

### ChangedFile

Описание одного изменённого файла в MR: путь, признаки (новый, удалён, бинарный,
переименование).

## Результат анализа

### Finding (находка)

Единичное замечание ревьюера: **severity**, **category**, файл и строки, краткое
**message**, опционально rationale, suggestion и confidence. Строительный блок
итогового отчёта.

### Severity

Серьёзность находки: `blocker` → `major` → `minor` → `nit`. Влияет на вердикт,
порядок сортировки и фильтрацию по **policy** (строгость проекта).

### Category

Классификация находки: `bug`, `security`, `perf`, `requirements`, `maintainability`,
`style`. Категория `requirements` — расхождение с задачей Kaiten, не синтаксическая
ошибка.

### Confidence

Уверенность движка в находке: `high`, `medium`, `low`. Используется для фильтрации
шума и настройки порогов.

### Verdict (вердикт)

Итоговая оценка MR на верхнем уровне:

| Значение | Смысл |
| --- | --- |
| `ok` | Критичных проблем не выявлено |
| `risks` | Есть значимые, но не блокирующие риски |
| `blockers` | Есть блокирующие проблемы |

Вердикт агрегируется из находок и покрытия критериев (берётся «худший» итог).

### ReviewResult

Полный результат одного прогона: **verdict**, текстовая **summary** для сводного
комментария, список **findings**, опционально **requirements_coverage** и заметки
**degradations** (что не удалось проанализировать).

### RequirementCoverage / requirements_coverage

Оценка **каждого критерия приёмки** связанной карточки: выполнен (`met`), частично
(`partial`), не выполнен (`missing`) или неизвестно (`unknown`), с опциональным
evidence (файл, строка, пояснение).

### Degradations

Явные пометки о пропусках: задача Kaiten не найдена, бинарный файл пропущен,
невалидный JSON от движка, таймаут части анализа. Ревью продолжается с тем, что
есть — принцип «деградация, а не отказ».

## Пайплайн: декомпозиция и постобработка

### Partition (декомпозиция)

Разбиение MR на `ReviewUnit` перед вызовом движка: фильтрация ignored/binary файлов,
нарезка по **бюджету контекста** (размер diff/файлов). В будущих фазах — группировка
по задачам из commit-map.

### Aggregate (агрегация)

Слияние результатов нескольких юнитов в один `ReviewResult`: дедупликация находок,
выбор **худшего** verdict и статуса критериев, объединение summary.

### Normalize (нормализация)

Постобработка находок после движка и агрегации: валидация по схеме, glob-фильтры
путей, пороги строгости (скрыть `nit` в режиме `balanced`), дедуп по fingerprint,
сортировка по severity, **cap** (верхняя граница числа публикуемых находок).

### Fingerprint (фингерпринт находки)

Стабильный идентификатор **смысла** находки — хэш от нормализованного пути, правила/
семантики сообщения и привязки к коду. **Не** привязан жёстко к номеру строки (строки
смещаются между коммитами). Нужен для идемпотентной публикации: обновить существующий
комментарий, не создавать дубликат; закрыть тред, если находка исчезла.

### Идемпотентность

Два уровня:

1. **Запуск** — `(project, mr, sha)` (+ версии промпта/partition) уже в state store →
   пропуск, если не force.
2. **Публикация** — сопоставление новых находок с ранее опубликованными по fingerprint;
   один сводный комментарий обновляется (edit), inline-треды создаются/закрываются
   идемпотентно.

### Policy (политика проекта)

Настройки ревью для конкретного GitLab-проекта: включён ли бот, `review_on` (триггеры),
фильтры файлов, строгость, лимиты diff, версия промпта. Накладывается поверх
глобального конфига; **discovery** определяет, какие проекты вообще кандидаты.

### Discovery

Как Mira узнаёт, **какие проекты** обслуживать: явный список (`explicit`), по
членству bot-аккаунта в группе (`membership`) или гибрид. Отделён от policy: сначала
«видим проект», затем «с какими настройками ревьюим».

## Режимы и инфраструктурные термины

### Dry-run

Режим публикации **без записи** во внешние системы: находки и сводка только в
структурированный лог. Текущий MVP использует dry-run; публикация в MR — фаза 2.

### State store

Внешнее хранилище состояния: какие SHA уже ревьюились, fingerprints, метрики.
Позволяет stateless-воркерам и горизонтальному масштабированию.

### Queue (очередь)

Буфер между триггером (poller/webhook) и воркером. MVP — in-process; позже — Redis
с retry/backoff и dead-letter.

### Headless CLI

Неинтерактивный запуск Cursor (`cursor-agent -p --output-format json`) как реализация
`ReviewEngine` в MVP.

### MCP (Model Context Protocol)

Протокол инструментов для агента (чтение Kaiten, GitLab). Не путать с Publisher:
запись комментариев в MR идёт через REST bot-токен, не через read-only MCP.
