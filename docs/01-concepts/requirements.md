# Требования и ограничения

Документ фиксирует **что** должен делать Mira с точки зрения продукта и эксплуатации.
Детали интеграций, конфигурации и реализации — в [../04-architecture/](../04-architecture/README.md)
и [../03-reference/](../03-reference/README.md).

## 1. Функциональные требования

### FR-1. Обнаружение событий MR

- **FR-1.1.** По умолчанию ревьюить **первичное состояние MR**: создание не-draft MR
  (`action=open`) и переход `draft → ready`. Последующие пуши (фиксы по замечаниям)
  **не** запускают автоматическое ревью — это снижает шум и стоимость.
- **FR-1.2.** Поддержать ручной перезапуск ревью командой в комментарии MR
  (`@mira review`) — он ревьюит актуальный коммит всегда, даже если автопуш-ревью
  выключено.
- **FR-1.3.** Сделать набор автотриггеров **настраиваемым** на уровне проекта
  (`review_on`): по умолчанию `[open, ready, manual]`; опционально добавить `push`
  (ревью каждого нового коммита, с debounce) для критичных репозиториев, либо свести
  к `[manual]`.
- **FR-1.4.** Игнорировать незначимые события (изменение лейблов, назначение
  ревьюеров, изменение заголовка) и системные события (`system: true`), кроме
  интересующих.

### FR-2. Сбор контекста

- **FR-2.1.** Получить diff MR, список изменённых файлов, метаданные MR (заголовок,
  описание, ветки, автор, target branch).
- **FR-2.2.** Разрешить связь **MR ↔ задача Kaiten** (несколько стратегий резолвера;
  канон — ID карточки в имени ветки + ссылка в описании MR, см. [roadmap.md](./roadmap.md)).
- **FR-2.3.** Получить из Kaiten описание задачи и критерии приёмки.
- **FR-2.4.** Дать агенту доступ к репозиторию на ветке MR (полный или частичный
  контекст файлов).
- **FR-2.5.** Опционально подтянуть конвенции репозитория (`.cursor/rules`, `AGENTS.md`,
  стайлгайды) как часть контекста.

### FR-3. Анализ (ревью)

- **FR-3.1.** Находить потенциальные **баги и регрессии** (логика, граничные случаи,
  null/ошибки, конкурентность, ресурсы).
- **FR-3.2.** Находить проблемы **безопасности** (инъекции, секреты в коде, авторизация).
- **FR-3.3.** Оценивать **соответствие задаче**: реализовано ли то, что требовалось;
  нет ли «лишнего» вне scope.
- **FR-3.4.** Опционально — производительность и поддерживаемость (настраиваемая строгость).
- **FR-3.5.** Выдавать **структурированные находки** по схеме (severity, категория,
  путь, строки, описание, предложение) + итоговый вердикт и покрытие критериев
  приёмки. Схема находок — [../03-reference/finding-schema.md](../03-reference/finding-schema.md).

### FR-4. Публикация результата

- **FR-4.1.** Публиковать сводку-комментарий в MR.
- **FR-4.2.** По возможности — inline-комментарии к конкретным строкам diff.
- **FR-4.3.** **Идемпотентность:** при повторном запуске обновлять/закрывать прежние
  замечания бота, не дублировать.
- **FR-4.4.** Опционально — дублировать краткую сводку в карточку Kaiten (комментарий;
  только через сервис-аккаунт, не личный токен).
- **FR-4.5.** Помечать пропуски/деградации («не удалось получить файл X»,
  «задача Kaiten не найдена»).

> На текущей фазе (MVP) publisher работает в режиме **dry-run** — находки пишутся в
> лог, в GitLab/Kaiten не публикуются. См. [domain-glossary.md](./domain-glossary.md).

### FR-5. Управление и конфигурация

- **FR-5.1.** Определять список подключённых проектов через **discovery** (по членству
  бот-пользователя в GitLab / явный список / гибрид) и включать-выключать ревью на
  уровне проекта/группы.
- **FR-5.2.** Настраивать фильтры файлов (игнор lock-файлов, сгенерированного кода, бинарей).
- **FR-5.3.** Настраивать пороги строгости и набор включённых категорий находок.
- **FR-5.4.** Настраивать модель Cursor и лимиты (таймауты, max размер diff).
- **FR-5.5.** Шаблоны промптов — версионируемые и переопределяемые на проект.

## 2. Нефункциональные требования

| Код | Требование | Целевое значение / примечание |
| --- | --- | --- |
| NFR-1 | Латентность | ≤ 3–5 мин до публикации ревью на средний MR |
| NFR-2 | Пропускная способность | Параллельная обработка N MR (конфигурируемая конкурентность воркеров) |
| NFR-3 | Надёжность | Очередь с повторами и backoff; падение одной задачи не роняет сервис |
| NFR-4 | Идемпотентность | Гарантирована на уровне `(MR, commit SHA)` |
| NFR-5 | Наблюдаемость | Структурные логи, метрики, корреляция по `run_id`/`agent_id` |
| NFR-6 | Безопасность | Секреты вне VCS; минимальные scope токенов; изоляция воркспейсов |
| NFR-7 | Конфиденциальность кода | Код уходит только в выбранный движок Cursor; контроль egress |
| NFR-8 | Стоимость | Контроль расхода токенов модели: лимиты на размер diff, дедуп, кэш |
| NFR-9 | Переносимость | Развёртывание контейнерами; не завязано на конкретную ОС хоста |
| NFR-10 | Расширяемость | Новый VCS/трекер/движок добавляется адаптером без правок ядра |

## 3. Ограничения (Constraints)

- **C-1.** **Без GitLab CI/CD pipelines.** Триггеры и оркестрация — вне `.gitlab-ci.yml`.
- **C-2.** Выделенный сервер с установленным Cursor CLI — целевая среда исполнения.
- **C-3.** GitLab — self-hosted (`gitlab.ai-referent.ru`), внутренняя сеть.
- **C-4.** Публикация комментариев в MR — через **GitLab REST под bot-токеном**
  выделенного аккаунта Mira (не через read-only MCP). См. [roadmap.md](./roadmap.md) Q-1.
- **C-5.** Kaiten под текущим личным токеном — **строго read-only**; запись в Kaiten
  только через будущий сервис-аккаунт.
- **C-6.** Доступ агента к интернету/внешним моделям ограничен политикой безопасности
  (egress на Cursor API согласован — см. [../05-operations/security.md](../05-operations/security.md)).

## 4. Допущения (Assumptions)

- **A-1.** На сервере можно установить и держать запущенными: Cursor CLI, runtime
  (Node), git, контейнеры.
- **A-2.** Можно создать сервис-аккаунт/деплой-токен GitLab с правом read репозитория и
  (после согласования) с правом писать комментарии в MR.
- **A-3.** Можно настроить **webhook** на проектах/группе GitLab (webhook ≠ pipeline,
  ограничение C-1 не нарушается).
- **A-4.** Есть `CURSOR_API_KEY` (пользовательский или сервис-аккаунт команды) с доступом
  к нужной модели (`composer-2.5`).
- **A-5.** В команде есть конвенция связывания MR с задачей Kaiten (или мы её введём).

## 5. Зависимости

- **D-1.** Cursor CLI / SDK и доступность Cursor API из сети сервера.
- **D-2.** GitLab API (read; write — по согласованию) и webhooks.
- **D-3.** Kaiten MCP/API.
- **D-4.** Инфраструктура: контейнеры, хранилище состояния (SQLite/Postgres),
  опционально брокер очереди (Redis).

## 6. Открытые вопросы (резюме)
