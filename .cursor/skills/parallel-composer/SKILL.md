# Parallel Composer

Максимально распараллеливай выполнение задачи: всё, что можно делать независимо,
делается одновременно подагентами `Task` на модели `composer-2.5-fast`.

## Когда применять

- Задача состоит из нескольких частей, которые не зависят друг от друга.
- Нужно ускорить большую работу (рефакторинг по многим файлам, генерация тестов,
  написание независимых модулей, миграции, массовый поиск/правки).

Если задача по сути линейна (каждый шаг зависит от предыдущего) — параллелить
нечего, выполняй последовательно и не плоди подагентов.

## Рабочий процесс

```
Progress:
- [ ] 1. Декомпозиция на подзадачи
- [ ] 2. Построение графа зависимостей (волны)
- [ ] 3. Запуск волны: максимум параллельных Task-агентов
- [ ] 4. Сбор результатов волны
- [ ] 5. Повтор для следующей волны, пока зависимости не закроются
- [ ] 6. Финальная сборка и проверка
```

### 1. Декомпозиция

Разбей задачу на наименьшие самодостаточные единицы работы. Каждая единица должна
завершаться без обращения к промежуточным результатам других единиц той же волны.

### 2. Граф зависимостей → волны

Сгруппируй подзадачи в «волны»:

- **Волна** — набор подзадач без зависимостей между собой → выполняются параллельно.
- Подзадача попадает в следующую волну, только если зависит от результата
  предыдущей. Минимизируй число волн, максимизируй ширину каждой.

### 3. Запуск волны (ключевое правило)

Запускай **все** подзадачи одной волны **в одном сообщении** — несколькими вызовами
`Task` подряд (это и есть параллелизм). Для каждого вызова:

- `subagent_type`: `generalPurpose` (для правок/многошаговых) или `explore`
  (только чтение/исследование).
- `model`: **`composer-2.5-fast`** — всегда для этого скилла.
- `run_in_background`: `true` — чтобы агенты шли одновременно, а не блокировали.
- `description`: 3–5 слов, уникально на каждый агент.
- `prompt`: полностью самодостаточный (подагент не видит этот чат): дай контекст,
  точные пути файлов, что сделать, ограничения и что именно вернуть в ответе.

Стремись к максимальной ширине волны. Если подзадач очень много — запусти столько
параллельных агентов, сколько есть независимых единиц, не дроби искусственно на
последовательные пачки.

### 4. Зоны записи без конфликтов

Чтобы параллельные правки не конфликтовали, давай каждому агенту **непересекающийся
набор файлов/директорий**. Общие файлы (конфиги, индексы, точки агрегации) правь
сам уже после сбора результатов, а не внутри параллельных агентов.

### 5. Сбор и следующая волна

После завершения волны собери результаты, затем запусти следующую волну тем же
способом. Не начинай зависимую подзадачу, пока её предпосылки не готовы.

### 6. Финальная сборка

Сам выполни шаги, требующие глобального согласования (объединение, правка общих
точек входа, прогон линтера/тестов), и проверь итог.

## Шаблон промпта для подагента

```
Контекст: <что за проект/задача, минимально необходимое>
Файлы в твоей зоне: <точные пути, только их>
Сделай: <конкретный результат>
Ограничения: <стиль, правила, чего НЕ трогать>
Верни: <краткий отчёт: что изменено, проблемы, что осталось>
```

## Анти-паттерны

- Запускать агентов по одному в разных сообщениях, когда они независимы (теряется параллелизм).
- Давать двум параллельным агентам один и тот же файл на запись.
- Параллелить шаги с реальной зависимостью по данным.
- Использовать `composer-2.5-fast` для задач, где пользователь явно просил другую модель.
